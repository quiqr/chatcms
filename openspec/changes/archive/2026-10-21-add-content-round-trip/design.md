## Context

`internal/model` reads a site's model; `internal/gitsync` supplies a working
copy and writes versions. What is missing is the thing in between: turning a
content file into values a form can edit, and turning them back into exactly
the bytes the old Quiqr would have written. See `proposal.md` for why that
last word matters.

The reference implementation is three small files in `../quiqr-desktop`:
`packages/backend/src/utils/format-providers/{yaml,toml,json}-format-provider.ts`.
They are thin wrappers, which means the real specification is the behaviour of
`js-yaml` at its defaults and `tomlify-j0.4` with `space: 2`.

## Goals / Non-Goals

**Goals:**

- A file written by the old Quiqr, read and written back, is the same file.
- An edit to one field changes one thing in the diff.
- Where ChatCMS cannot be certain it matches, it refuses rather than guesses.

**Non-Goals:**

- A general-purpose YAML library. This emitter serves the value shapes a Quiqr
  model can hold and is not correct outside them, on purpose.
- The browser side of the form. See the assumption in `proposal.md`.
- Media and bundles, which the media epic owns.

## Decisions

### The emitter is written here, because no Go library produces these bytes

This is the uncomfortable decision and it is the right one. `js-yaml` at its
defaults produces output that no Go YAML library reproduces: sequences
indented under their key, single quotes rather than double, folded blocks at a
width of eighty, `null` spelled out, and a specific table of when a scalar
needs quoting. Using `gopkg.in/yaml.v3` or `goccy/go-yaml` and accepting the
difference would rewrite every file in a customer's repository the first time
anyone pressed save.

Observed, by running `js-yaml` rather than by reading its source:

```yaml
tags:                      # sequences indent under the key
  - news
a: 'yes'                   # quoted: would otherwise be a boolean
b: '123'                   # quoted: would otherwise be a number
d: it's                    # not quoted: an apostrophe alone is fine
e: |                       # multi-line becomes a literal block
  multi
  line
summary: >-                # long lines fold at 80
  This is a fairly long summary that will certainly exceed the default line
  width that js-yaml uses when it dumps a document.
title: null                # not ~, not empty
empty: ''
tags: []
obj: {}
```

Each of those lines is a test case, and each expected value is generated by
running `js-yaml`, not typed from this document.

### Unsupported shapes are an error, not a guess

The emitter handles the shapes a model can produce. Anything else, a value
with a type the table does not cover, fails the save and names the field. A
CMS that writes something slightly different from what it promised is worse
than one that says it cannot write this yet, because the first is discovered
by a customer and the second by us.

This is what makes writing the emitter safe: its correctness claim is bounded
and the boundary is enforced at runtime.

### Goldens are generated by running the reference, and the script is not in the gate

`scripts/generate-goldens.sh` runs Node with `js-yaml` and `tomlify-j0.4` over
a table of values, and writes the result next to the fixtures. The Go tests
read those files. The script needs the network the first time it installs the
two packages, so it is never part of `nix flake check`; its output is
committed and the gate compares against it.

The alternative, writing the expected bytes by hand, would make the test agree
with what I believe `js-yaml` does. The whole point is to find out where that
belief is wrong.

### Reading keeps the document, not just the values

A parsed document keeps its original bytes, the parsed values, and the key
order it had. Writing rebuilds from the values but follows the original order
for keys that were there, appending new ones in the order the model declares
them. That is what the reference does, because a JavaScript object preserves
insertion order and the object came from parsing the file.

This also makes the "an edit changes only what was edited" requirement
achievable without surgical byte editing: the emitter is deterministic, so
emitting the same values twice gives the same bytes, and emitting values that
differ in one place gives bytes that differ in one place.

### The field tree is walked, not the data

Mapping values to fields walks the model's fields and pulls each one's value
out of the data tree, rather than walking the data and guessing which field
owns what. A value no field claims stays in the document untouched and is
written back where it was. That is how "nothing in a document is lost" is kept
without a list of exceptions.

Placement rules, taken from the reference application's field components:

| Field         | Where its children's values live        |
| ------------- | ---------------------------------------- |
| `section`     | under its key, unless `groupdata: false` |
| `nest`        | under its key, unless `groupdata: false` |
| `pull`        | under `group`, or its key when absent    |
| `accordion`   | a list of objects under its key          |
| `leaf-array`  | a list of the child's values under its key |

### The body is the field whose value is the Markdown

The reference calls it `mainContent` and treats it as one more key, splitting
it out when writing. The same convention is kept, so a model that declares a
`markdown` field with that key edits the body, which is what existing models
do.

## Risks / Trade-offs

- **A hand-written emitter will have gaps.** Mitigated by the refusal rule: a
  shape it has not been proven against fails rather than differs. The failure
  is loud, local and fixable; a silent difference is none of those.
- **`js-yaml` could change its output in a future version.** The customer's
  files were written by the version they ran. Mitigated by recording which
  version generated the goldens, so a mismatch is traceable rather than
  mysterious.
- **Folding is the fiddliest part.** Mitigated by generating goldens for
  strings around and far past the boundary, including ones with no space to
  break at, and by asserting that reading the folded result back gives the
  original string.
- **Key order depends on how the file was parsed.** A parser that returns a
  map loses it. Mitigated by keeping order explicitly alongside the values
  rather than relying on any map.

## Migration Plan

Nothing is deployed and no file is rewritten by this change. The first time
ChatCMS saves a page in a customer's repository is the moment this contract is
tested for real, which is why acceptance test 3 runs against the customer site
rather than only against fixtures.

## Open Questions

- Whether any customer site uses JSON front matter. The emitter covers it
  because the reference does, but no fixture has been seen in the wild.
