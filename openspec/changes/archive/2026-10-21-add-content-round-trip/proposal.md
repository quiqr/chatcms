## Why

The single most important promise in this project is that ChatCMS can edit a
site the old Quiqr desktop app edits, and leave the files looking the same.
`docs/TESTING.md` calls it the backwards-compatibility contract, and
`docs/BRIEFING-M01.md` section 2 states it plainly: saving through a form must
produce the same front matter and Markdown as the old Quiqr. Epic
`chatcms-sbe1`.

It serves acceptance test 3, and nothing that writes content can be built
before it.

## What Changes

- **A content file becomes values, and values become a content file.** Reading
  splits front matter from the Markdown body, parses it in whichever of the
  three formats the file uses, and maps it onto the model's field tree. Writing
  reverses that exactly.
- **The field tree decides where a value lives.** A `section` nests its
  children under its own key unless it says otherwise; a `pull` nests them
  under a key it names; an `accordion` is a list of objects; a `leaf-array` is
  a list of scalars. Getting this wrong moves a customer's data.
- **YAML is written byte for byte as the reference writes it.** The old Quiqr
  writes YAML with `js-yaml` at its defaults. This change reproduces that
  output in Go, including the parts that are arbitrary: single-quoted scalars,
  two-space indentation with indented sequences, literal blocks for multi-line
  strings, folded blocks at a line width of eighty, and the exact spelling of
  null, empty strings, empty lists and empty objects. Every Quiqr site uses
  YAML front matter.
- **TOML and JSON front matter is read, and writing it is refused for now.**
  The reference writes TOML in a layout it cannot read back, so reproducing it
  would produce files nothing can open. See the assumption below.
- **Goldens are generated by running the reference implementation**, not
  written by hand. A script runs `js-yaml` and `tomlify-j0.4` over a table of
  values and records their output; the Go tests assert equality with it. When
  the two disagree, the reference wins.
- **Anything that cannot be reproduced faithfully fails loudly.** A value
  shape the emitter has not been proven against is an error at save time, not
  a quiet difference in a customer's repository.

## Capabilities

### New Capabilities

- `content/document`: what a content file is, how it is split into front
  matter and body, and how values map onto a model's fields.
- `content/serialisation`: how values are written back, and the guarantee that
  the bytes match what the reference implementation produces.

### Modified Capabilities

None.

## Impact

- **New code**: `internal/forms`, and `internal/frontmatter` for the emitters.
- **New fixtures**: `test/fixtures/content/`, with goldens produced by the
  reference implementation.
- **New tooling**: `scripts/generate-goldens.sh`, which needs Node and the two
  reference packages. It is run by hand when a case is added, never by the
  gate, and its output is committed.
- **A known limit**: a page whose front matter is TOML or JSON can be read but
  not saved, with an error that says so rather than a file nobody can open.
- **Dependencies added**: none in Go. The emitters are written here precisely
  because no Go YAML library produces `js-yaml`'s output.
- **Seams**: none of the four in `docs/ARCHITECTURE.md`. `internal/forms`
  reads through an `fs.FS` and returns bytes, so `internal/gitsync` supplies
  the working copy and performs the save.
- **Coverage**: `internal/forms` becomes the last of the four core packages to
  carry the 80% floor, leaving only `internal/policy` absent.

## Assumptions

- **This change is the first half of its epic.** The epic also covers the
  browser-side field renderers, the Markdown body editor, field-to-preview
  linking and autosave. Those are interface work that belongs after the design
  foundation epic, which has not shipped; building them now would mean
  building them twice. The bean stays in progress and a second change closes
  it. The contract in this change blocks nothing else and is what acceptance
  test 3 actually tests.
- **The emitter covers what a Quiqr model can produce.** Strings, numbers,
  booleans, dates, null, lists of scalars, lists of objects, and nested
  objects. A shape outside that set is an error rather than a guess.
- **Writing TOML is refused, because the reference writes it broken.**
  `tomlify-j0.4` returns no trailing newline, and the reference puts the
  closing `+++` straight after the last value. Its own reader looks for that
  delimiter at the start of a line, so it never finds it and reads the whole
  file as body. Verified by running both halves of the reference against each
  other. Reproducing that exactly would write files neither application can
  open; writing valid TOML instead would differ from the reference on every
  byte after the last value. Reading TOML works, so no existing page becomes
  unreadable; saving one reports the limit. JSON front matter is refused for
  writing on the same principle, having never been seen in a real site.
- **Line folding is reproduced, not avoided.** `js-yaml` folds a long scalar
  at a width of eighty. Writing such a scalar unfolded would differ from the
  old Quiqr on the very first save of any page with a long summary, so the
  folding algorithm is implemented and tested against generated goldens.
- **Key order follows the data, not the model.** The reference implementation
  dumps a JavaScript object in its own key order, which for a file that was
  read and then written is the order the file had. New keys are appended in
  the order the model declares them, which is what the reference does when a
  form adds a value.
- **`bundle-manager` moves files, not values.** It is read and carried, and
  the media epic owns what it does. Nothing in this change writes a bundle.
